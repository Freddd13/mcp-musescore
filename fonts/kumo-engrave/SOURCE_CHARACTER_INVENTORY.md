# 实际源字符清点：控制码、空格和 U+0000

2026-10-19。全目录索引已从 schema 2 改为 schema 3，重新只读扫描全部 **146 份 PDF、1,135 页**。本轮修正清点工具和覆盖证据；**生产字体仍为 0.500，OTF、字宽、Text 校准均未改变，无需重新安装。** 上轮：[隐藏字体全对象核查](HIDDEN_FONT_COVERAGE.md)；总计划：[FONT_PLAN](../../docs/FONT_PLAN.md)。

## 为什么旧方法会漏

PDF 的字符编号不是可靠的音乐语义。旧清点使用 `obj.extract().strip()` 和 Unicode 空白判断，会漏掉实际表示括号、等号或普通字母的控制码；没有 Unicode 映射的字还可能显示为 U+0000。反过来，提取器为阅读文本生成的空格也不一定是原 PDF 的字符。

新版按 PDFium 实际字符索引取得 Unicode、所属文字对象及生成标志，保留空格、控制码、U+0000 和映射错误标志，排除生成字符。每个键限定在“具体 PDF＋字体名＋编码”内，不能把同名字体的编码跨 PDF 套用。字体名分类仍只是候选筛选，不能代替看图识别。使用的接口见 [PDFium 官方 fpdf_text.h](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/public/fpdf_text.h)。

结果为 **925,005 个实际源字符、1,435,137 个生成字符，实际源字符未归属对象为 0**。所有原件 SHA、页数、文字对象数量和字体名集合与旧清点一致。新证据写入独立目录 `dist/corpus-v3-176/`，旧 `corpus-v2/` 保留；工具拒绝覆盖不同 schema 或来源已变化的检查点。

## 补查结果和具体误判

相对旧表新增 595 个逐 PDF 字体／编码键，对应 6,813 个实际源字符位置。其中 561 个键为 U+0020；这些是清点键数量，不能写成新增了 595 种符号。

全部新增位置已回原文字对象渲染。初筛 503 个代表，21 张图表已逐张审视，其中 13 个为音乐复合对象或音乐符号，490 个为标题、署名、页码、表情词及旋转的普通文字。音乐候选如下；括号在具体谱中的用途仍需看音符／变音上下文，不据外形唯一认定用途。

| 原 PDF／字体／编码 | 实际图形 | 当前处理 |
| --- | --- | --- |
| A024 Chaconne U+000B | 左括号 | 已有左右音符／变音括号字形，不新增 |
| A036、A055 Chaconne U+000B／000C | 左／右括号，常在同一对象内成对出现 | 逐码区分方向，不把整对当单字 |
| A057 FEF4ADEE9C2 U+0009 | 速度四分音符旁的等号 | 独立字符裁图确认等号；已有 `timeSigEquals` |
| A082 Chaconne U+0085 | 叉形符头 | 已有 `noteheadXBlack` |
| A057 FEF41169AFD U+0009–000D | t、d、m、a、词间空格 | 普通表情文字编码，接续 H112 的逐词解码，不映射音乐符号 |
| A057 Palatino 的若干控制码 | 标题、署名、版权行及页码 | 普通文字，不能因编码看似异常而换成音乐字形 |

源字符是空格时，字符框裁图偶尔包含相邻斜体或衬线字母墨迹；所以初筛状态名 `visible-target-character-review` 只表示需要看图，**不证明空格本身有可见字形**。这批代表显示的都是普通文字，不据裁图黑像素数量发明新音乐符号。

72 个整对象提取位图没有墨迹的对象（100 个新增字符位置），已逐个在原页中只激活该对象：整页 2x 和局部 32x 均纯白，57 个源页可见文字对象对照通过。包含 Kousaku 的 16 个空对象。1,001 个页外位置另列，不与页内纯白混为一类。PDF 只读，激活状态仅在内存变化并恢复，未保存 PDF。

U+0000 即使没有 `HasUnicodeMapError` 标志，也不能按字符串去重。为此另外检查了**全部 17 个可见 U+0000 对象**，不是仅选两个代表：A125 的 10 个对象为文件名式标题／页脚；A132 的 7 个对象为标题、署名、版权和 `poco a poco cresc.`。其余 42 个 U+0000 位置属于上述纯白对象。未来初筛已改为 U+0000 按图像区分代表。

旧表消失的两项“空格字”是 A125 FEF3203D4E1 和 A132 FEFC71BC52D 的提取文本假象。重新扫描这两个家族全部 11 个对象：实际源字符分别为 366 和 9 个 U+0000，实际 U+0020 均为 0；可见文字已纳入上述逐对象检查，不能将它们记为两个缺失字形。

## 大小保护与当前边界

用户再次强调 mf、八度等应保持合理实际大小。当前版本保留 0.480 的修复：同宿主、同谱距下，mf 高度约为改名 Leland Text 基线的 96.1%，8 为 100.9%，8va 为 98.5%；踏板及解除星号也接近基线。基线不是用户历史 PDF 的逐对象重建。本轮检查两份生产 OTF 的 SHA 与上轮完全一致，**没有重跑未发生变化的原生渲染，也不声称新增了大小验收**；有效尺寸证据仍为 `dist/native-size-audit-145/`，详见 [TEXT_SIZING](TEXT_SIZING.md)。

后续修改继续在相同谱距、完整上下两手、原字号和局部覆盖下比较实际墨迹大小、字宽及归属；独立字形图只用于观察轮廓。Music 与 Text 分开校准，不能把同一 EM 轮廓直接复制到两者，也不能用修改原谱字号掩盖字体缩小。若有意偏离现有尺寸，先交付同尺度少量候选及阅读理由。

这次关闭了全目录索引的控制码遗漏、已新增键的代表识别、全部纯白对象和全部可见 U+0000 对象队列；没有新增必须制作的音乐角色。它不等于全目录每个同码异形、每次出现的语义和所有大小都已分别认证。全目标仍在进行，下一步使用 schema 3 按实际形状核对剩余同码差异；未验证的内容保持 Leland 或已有已验证字形，不凭编号乱替换。
