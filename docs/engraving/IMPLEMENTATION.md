# 从规范依据到可执行净书

日期：2026-10-09。当前完成首批依据库，以下实现均为**后续路线**，没有新增已可调用工具。

## 现在就可以调，但应在独立副本验证

入口名称可能随语言/个人分支变化；使用实际有效样式而非仅检查 MSCX 中显式保存的标签。历史试验能帮助选方向，但本批未再次把这些候选写入任何乐谱。

## 当前 MCP 是否足够

净书判断本身不依赖 MCP：只读工程解析、PDF/原生导出、规则和案例都可以先进行。MCP 是 Codex 操作宿主的一种接口，插件也可以本地独立提供诊断。

当前 `get_score_data` 支持音符/声部、真实时长、逐音延音等分析，但尚不构成完整净书诊断：没有统一返回最终布局坐标/曲线、有效样式、所有文字跨度/作用域、实际可见谱表映射，也没有局部预览/原生导出的专用工具。现有 VexFlow/LilyPond 预览不是 Evolution 排版效果；不能用其判断字形、碰撞和分页。

基于本批只读源码核查：

- 本体 `libmscore/beam.cpp` 在约 216/549/2569 行按 `Sid::beamWidth` 生成梁轮廓；1567–1569 行结合 `beamWidth` 与 `beamDistance` 算梁间距离。这支持梁主体是引擎几何，不能归因到字体轮廓。
- `libmscore/dynamic.cpp` 约 97 行构造范围为 `Range::PART`，202–203 行读 `dynType`，488–489 行给范围默认值；`dynamic.h` 描述 STAFF/PART/SYSTEM。m41 的 mf、pp 没有 `dynType`。**当前范围模型不等于 Dorico 的 voice-specific dynamics**。
- `src/tools/connection.py` 的 `get_score_data` 从现有整谱读数筛选小节；分段参数不意味着宿主只遍历指定范围。大谱效率不能仅从接口签名判断。

源码仓库有其他并发任务，以上行号可能变化；不修改软件本体，定位时按函数/属性重查。结构事实与音乐表达的真实意图仍需分开。

## 阶段 B：先做可复核的只读诊断

**B1：离线工程审计。** 解包只读 MSCZ 到隔离目录；提取有效拍号/拍组、声部、逐音延音、文字/跨度起止、力度范围、staffMove、可见性、break/spacer 与显式 offset。补足默认值，避免把“没保存标签”当零值。输出地址和来源，不做写入。

第一个范围选 E08/E09/E13：m41 的时间/范围与手动位置，m111–114 的文字/弧/技术提示关系，以及第 2 页的垂直空白。m148–149 四谱表作为必需反例。文件解析先完成；只有需要当前窗口或原生对象数据时，再增加本地插件读取。

**B2：原生几何对照。** 在同版本 Evolution、正常 Windows 字体环境下导出独立副本，关联页面/系统/显示谱表/segment 与原生对象。PDF 只能补充墨迹与实际尺寸，不能取代全部语义。先测局部曲线净距与归属，再考虑整页统计；不要只用矩形相交报错。

**B3：诊断报告。** 每项输出 `规则ID / 源对象地址 / 可见事实 / 语义与范围 / 候选 / 不确定项 / 验收`。区分必须修复、可能歧义、个人偏好，不能把所有参差都标成缺陷。音高/拼写/时点/时值/声部/逐音 tie/标记范围以结构比较守护。

通过条件：报告能精确定位与复现，E09 不合并 mf/pp，E12 不把行中段落当错误，E14 不从局部休止确定空手；GUI 版本另验证选择、撤销栈与保存状态不变。没有对应字段的项目明确为 unknown。

## 阶段 C：有限候选与局部预览

优先候选：E08 的语气文字通道；E10 的弧肩部/文字分离；E13 的局部垂直空白。一次只改变一个因素。每项至少保留原布局和两个有理由的候选，展示阅读收益与新代价，允许保持原样。

原生渲染负责验收；规则/确定性计算负责候选，Codex 负责解释和上下文歧义。语义保护使用严格条件；净距、归组、一致性、伸缩量与改动范围作偏好比较。先生成副本和差异，不写当前谱。实际应用时要有明确作用域、旧值匹配与过期检查、一次原生撤销，以及失败后的已应用项清单。

格式建议：地址应含工程 revision/hash、measure/tick/track、对象类型与稳定标识。公开接口只暴露有定义的读/改操作；不要为了便利开放任意 QML 执行。字体变更记录字体/元数据版本，防止旧几何候选复用到新字形。

## 阶段 D：系统与页面候选

在局部净距可信后，根据原生小节宽度生成少量断行候选，保留用户锁定/手动 break；对页数、结构导航、跨组/弧续段、水平压缩、垂直伸展分别列代价。需要实际翻页的边界再加入手空闲与演奏窗口约束。先用小范围动态规划/枚举证明收益，不直接改写整个布局引擎。

## 插件、MCP、本体的开发顺序

1. **离线工具/本地插件**：先读取、诊断、展示候选和处理副本。当前阶段最优先，无需为了研究先扩 MCP。
2. **定向 MCP 封装**：当本地操作稳定后，考虑 `get_engraving_context`、`analyze_engraving`、`preview_engraving_patch`、`apply_engraving_patch` 等范围明确的工具名。这些都是提议，尚未注册。读取与写入分离，保证版本、范围和结果可核验。
3. **最小本体接口**：只有 Plugin API 无法可靠提供必需的最终坐标/曲线/有效样式或原生事务，且已有复现案例时，再提独立、通用、只读优先的接口。性能缺口先测量。不要为了尚未验证的评分模型修改引擎。

真正涉及软件功能变更时，按 AGENTS.md 同步软件仓库用户指南、开发日志与提交；当前仅研究文档，不把未来工具写成已发布功能。

## 与字体任务交接

已通知任务“音乐字体开发”：E05 的多层梁和符头连接、E09 的时间/力度范围保护、E14 的四谱表密集与持音案例。字体线保留基本字库和度量，提供版本、字形/外框/锚点变化与配套 Text；净书线提供阅读需求和案例。

字体初步报告称原型保留 hmtx/字宽与普通符干锚点、只替换三个常规符头，另更新相关 cutout/分叉锚点，尚待原生验收。**字宽相同也不代表碰撞轮廓完全相同**，需要对照实际墨迹与 metadata。此处记录交接信息，不替字体线确认结果。

后续交接发现：字体任务原生试验中，只改名的 Maestro Text 对照也改变 mf/mp；报告基础 Text 缺少 dynamicMezzo，内置家族名享有 Leland Text 替代，改名家族可能触发 Bravura Text 整段回退。因此下一步各音乐字体变体先统一保留 Finale Maestro Text，才能较好隔离符头因素；字体“成功加载”或“轮廓/字宽未改”不足以证明 Text 显示等效。字体任务报告当前 0.17 四组原生输出均 9 页，原 PDF m148–149 的第 8 页片段在新输出第 9 页；后续定位要用小节/对象关联，不能沿用旧 PDF 页码。此段为另一任务的验证交接，具体构建和验收由字体线维护。
