# 原生导出的配置目录与运行资源复核

2026-10-22。这是[输入历史](INPUT_HISTORY.md)的补充，记录本轮实际发现及此前表述的更正；不把启动失败归为净书缺陷。

## 本次发现

此前部分研究把传入新的 `-c <路径>`直接表述成配置隔离。这个依据不充分。本机只读源码 `mscore/musescore.cpp` 的 `MuseScoreApplication::setCustomConfigFolder()` 只有在路径**已经存在且是目录**时才设置 QSettings 路径及 dataPath，否则返回 false；命令行调用处没有据此报错。源码与本次固定二进制的构建提交对应关系尚未确认，下面另列实际运行结果。

本轮先建立实际存在的私有配置目录，用此前固定的缩减运行时导出新原创谱，退出码为 3221226505（0xC0000409），没有生成预期文件。同一目录下，已知可用的旧原创谱也失败。改用不存在的配置路径，旧、新输入都能导出，但这些路径没有被创建。因此这些成功不能证明配置隔离，也不能拿来替代本轮正式比较。没有复制或修改用户配置；不能反过来宣称这些历史调用绝未读取用户设置。

## 本轮怎样重建共同环境

保留原有缩减副本，新建另一个私有运行时：

- 沿用固定 bin／instruments／styles，EXE SHA-256 仍为 `7b4e6fbfdee1863a4801f018535fa6b2082500d9a2b851dc79579b9ace95aa25`。
- 从本机安装目录加入 workspaces、qml、workflow、locale、plugins、templates、tours、wallpaper；没有替换 bin，也未修改安装目录。没有逐目录排除，所以没有定位究竟哪个资源消除了故障。
- 用同一个**事先存在**的私有配置目录，旧原创谱和本轮新谱均能导出。随后所有正式比较都在这套环境重画；运行时 1936 个文件的大小／哈希在导出后对照复制清单复核。

实际目录、完整资源清单、首次失败、未接受配置路径的诊断导出及正式输出保留在本机忽略目录 `tmp/engraving/leading-reserve-2026-10-21/`。目录沿用研究开始日期，复核日期为10月22日。配置目录生成了 `workspaces/global/menubar.xml`。本轮称“预建私有配置目录下的共同环境”，不把 EXE 哈希相同升级为源码提交对应、全部环境依赖已隔绝或在别的机器必然可复现。

## 对旧记录的更正范围

[换谱号证据](clef_reading_evidence.json)曾明确写“Isolated per variant and format…No GUI or user config used”。本轮检查其私有研究目录，没有找到所述配置目录，原生调用缺少足以确认预建目录的记录。已为该字段增加日期与限定：**此前配置隔离未验证**。未声称本轮重跑了该研究；原先音乐配方、MIDI和图面比较仍是当时已记录的结果，重新复现时需重建共同环境。

另在八度／谱号研究的部分脚本中发现只构造新 `-c` 路径、未先建目录；这同样削弱相应隔离表述。当前不是全部历史导出的审计，不能由一个目录现状推断所有旧研究的实际设置。原有输入、输出和失败记录均保留，不追写成已经使用本轮环境。

## 后续原生试验的具体做法

导出前创建并核实私有配置目录，固定实际可工作的资源集合，先让共同基线在该环境成功。单凭退出码为0或命令里有 `-c` 不足以证明隔离。配置确实启用后若宿主失败，保留错误和已知输入对照；补齐资源或更换经过说明的共同环境，再重绘相关条件，不能悄悄退回一个不存在的配置路径。

这项更正没有改变记谱规范，也没有修改 MuseScore、插件、MCP、用户谱或字体。当前[行首留白研究](LEADING_RESERVE.md)的正式比较使用的是上述重建环境。
