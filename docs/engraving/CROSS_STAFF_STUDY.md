# 跨谱表：组织一个动作，而非只把图形搬过去

[滑奏续学](GLISSANDO_READING.md)进一步区分跨表动作线、声部引导和slur。A010同页有两类斜线，A047 Coda有双滑奏与换谱号／八度；不能以斜线最近音头自动建连接，也不由叉头的内部数字音高推定精确落键。用户副本仅改线形的原生与交换结论分记，未重写声部／奏法。

2026-10-20续补琶音成员、分组与净空，见第5–7节。此前从A045连续和弦、A050接力和A051分层力度回查Gould，实际完整查看印刷p316–318、320–322、325共7页。主PDF与页码映射见[教材记录](BEHIND_BARS_NOTES.md)。已有p315的最短干条件另见[梁干专题](BEAM_STEM_STUDY.md)，不混作同谱表的一般长度。

## 1. 副梁的边角为什么影响阅读（p316–317）

主梁已经连接整组，副梁应把细分显示清楚。若某个细分的干都同向，或两端干同向，副梁通常放在那一侧；短副梁也遵循相应条件，避免边角突出。细分两端干异向时，还要看它在主梁开头还是结尾；不是一律靠第一音或最后音。

当多种情境接在一起，保持副梁在同一侧有时更清楚：上下反复切换会显得像多了一层梁。这是为何“统一黑条几何”必须有节奏依据，而不是将梁视为字体。需要检查整组梁数、端点和白缝，再比较候选。

A045 p11 T的厚和弦提供真实上下文：共同梁帮助追踪交替动作；未来应自制不同细分/短副梁的样例验证。当前未证明本机存在相关错误，不直接提出本体修复。

## 2. 休止不总要两手各写满，也不能随便藏（p317–318）

单线跨手运行，只要拍点清楚，可把休止放在这条线所属的位置。细分边缘的休止靠同一细分，其内部休止一般靠后接音所在谱表；整拍休止则较宜两谱表重复，让其它拍定位清楚。两种可接受方案可以在简洁与明确之间取舍。

中间共同休止在双向干共梁情境中可以有效；若其它位置没有共同梁，读者突然要转去系统中央找休止，会增加搜索。不能把“所有休止居中”当一种整齐样式。严格对位的独立休止又是另一种情境，见既有教材笔记。

A046 p6 K上方休止、下方先发音是保护起点的例子；不能未经结构确认把它套成可省的单线休止。自制测试必须分单线交替、独立两部、整拍共同停三种。

## 3. 括号与弧线要让眼睛相信“这些音都属于它”（p320–322）

连续跨谱表连音可用较显眼、统一在上方的数字/括号；偶发组也可靠外端音或多数音所在侧。没有连梁的单线跨表组，干朝中间有助于识别整体；两端在不同谱表时，括号端要指向各自对象。若两端同表，括号仍须明显包含另一表的音，不能形式上连接正确、视觉上却像漏掉一手。

Slur同样不仅是“离外框多少”。一般两手可各有弧，低表下方放弧可为中间力度腾通道；一个跨表动作则应包含全组。双向干组的弧不应穿梁，某些情境可以接到干端，避免离相关音太远造成排除感。内层跨表slur特别难排，教材建议尽量避免；这不是允许自动删除原有分句的授权。

A044 p1/p7大拱运行、A042 p4下行接力可作范围检查。候选需看完整动作及相邻声部，不能只求一条曲线自身光滑。

## 4. 八度范围需要防止误读（p325）

共梁仅一手需八度转移时，局部符号应只包住相关音；实在难以分开，可明确另一谱表为loco。教材也指出八度符号通常作用于谱表的所有部，尽量避免同表同时有转移/原位两种音，必要可用另一谱表；空间不足的例外必须把范围讲清。

所以不能把“手”“软件voice”“显示谱表”“八度符号的播放范围”当作同一字段。A030 p5的上下局部八度、A051 p5的r.h.，都是范围审计的线索，PDF本身无法证明编辑对象的连接。先保护音高与时点；线高、折降和端点净空才是随后可试的外观项。

## 5. 琶音线为什么连续、分开，又不一定对齐

2026-10-20完整读图Gould印刷p131–133／主PDF p151–153：p131复读，p132补完整图，p133接完动态与时序，不宣称全章节完成。

**先辨动作。** 两谱表共同作一次连续展开，用一根贯通线；两手同时各展开自己的和弦，用两根独立线。需要箭头时分别说明各组方向。独立线可因变音列左右错开，不必强拉同X，更不能为了齐整合成一根。这是条件性记谱惯例，不是个人喜欢哪种线形的投票。

**线长解释成员。** 线覆盖被展开的音头，而非符干全长或当时所有可见音。A089《Michishirube》PDF p6末系统，最终新和弦前有一根跨表线；更低的音从前小节以tie接入，线在它上方结束。读者可区分延续低音与本次新展开。拉到最下面虽显得“完整”，却可能误示重弹低音；断成两根则可能误示两组同时开始。这里由可见tie／线端解释阅读用途，不声称知道内部voice、播放设置或出版者亲述意图。定位／哈希及本机高分辨裁图路径见[证据](arpeggio_reading_evidence.json)，原图不入Git。

**时序另查。** p133给出拍前展开、但须考虑演奏风格的惯例；拍上开始可文字说明或写出连续音。速度很慢、顺序不单调时，写出音序也更明确，代价是更多头、连接与空间。线在和弦左边不能独自决定声音时点，不能全改某个播放模式。p132的持续琶音说明、取消琶音括形，以及p132–133贯穿展开的竖向力度发夹，分别有持续／取消／动态作用，不按“竖线很乱”清理。

## 6. 原生练习：解决避让，保留有理由的不齐

## 7. 交换与未来需求：不能只数琶音符号

[MusicXML 4.0一手定义](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/arpeggiate/)按音记录参与者，number区分共同／独立组，unbroken可提示跨表贯通。格式可表达这些关系，不能将软件行为说成格式做不到。

实际连续版导出为4.0，却只给上表三音写arpeggiate，下表成员遗漏。重导入后span变1，图面只剩上方短线、下和弦同时奏；原生拍上／70ms字段也未保留。因此播放变化同时涉及成员和播放配置，不全归分组。8头、2休止、tie与计量内容仍在，两个整小节休止duration文本4/4变成等值1/1；布局也变化，交换结果不能替代原工程。两组版虽导出六个参与音，却未写number／unbroken；本次没重导入该版，不据数量推断独立组保留。一根原生波线又会绘成多个SVG字形片段，path数不是逻辑线数。

自动跨表降号避让已有原创复现，本例用局部留白＋线偏移可解，现阶段无需补丁。后续应补不同voice、方向、混合延续音和密度，再判断跨表成员与变音轮廓的排距／接口需求。当前只读源码的同voice轨道、几何及播放筛选可提示检查方向，但二进制与源码提交对应未证明，以实测输出为本机结论。见[完整证据](arpeggio_reading_evidence.json)；本轮没有修改MuseScore、插件、MCP或用户工程。

## 如何进入后续诊断

每个问题先写读者要追哪条线、看哪些拍点，再查梁数/干向、休止归属、括号是否包括全组、弧是否穿梁、八度有无歧义；琶音另查成员、延续低音、共同／独立展开、方向与时序。零碰撞、最短线长或最小面积不能独立决定最好方案。固定字体、原生对照和语义／读法核查通过后，才考虑交插件执行；已补一种琶音原生情境，其它跨表类型不因本例通过而视为实现。
